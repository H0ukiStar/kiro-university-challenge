# 安全のためのガードレール

EIP の解放は不可逆。以下は誤削除を防ぐための実務チェックリストと運用ルール。

## 解放前チェックリスト

各候補について、以下をすべて確認してから解放する。1 つでも「不明」があれば解放しない。

- [ ] `AssociationId` が本当に空か（使用中を候補に含めていないか）
- [ ] BYOIP ではないか（`PublicIpv4Pool` が `amazon`）
- [ ] 停止中インスタンスへの再アタッチ運用がないか
- [ ] IaC（Terraform / CloudFormation / CDK）で管理されていないか
- [ ] allowlist / ファイアウォール / パートナー登録の送信元 IP でないか
- [ ] DNS（A レコード）に紐づいていないか
- [ ] 対象リージョン・アカウントが想定どおりか（別環境の本番を触っていないか）

## 運用ルール

1. **必ずドライランを先に実行する。** 解放対象の全件を人間が見てから実行に移る。
2. **既定は対話確認。** `--yes` 相当の一括自動は、規模的に対話が非現実的な場合に限り、ユーザの明示合意を得てから使う。
3. **本番アカウントでは特に慎重に。** 認証プロファイル/アカウント ID を確認し、意図した環境かを実行前に提示する。
4. **中断可能にする。** 対話中に EOF（Ctrl+D など）や中断が来たら、残りは解放せず安全に停止する。
5. **消しすぎない。** 迷ったら残す。EIP の再課金は小さいが、誤解放の復旧コストは大きい（同じ IP は戻らない）。

## AI エージェントとして作業する際の追加ルール

このスキルに従って解放を代行する場合:

- **解放（`release-address`）は破壊的で不可逆な操作**として扱う。実行前に対象一覧をユーザに提示し、明示的な承認を得る。
- ユーザが「全部消して」と言っても、まずドライランの一覧を見せて件数と内容を確認してもらう。
- 検出（`describe-addresses`）など読み取り専用の操作は承認なしで進めてよい。
- 認証情報（アクセスキー等）の値を出力に含めない。プロファイル名やアカウント ID の参照に留める。
- 失敗した解放を、成功したかのように報告しない。件数と理由を正確に伝える。

## よくある事故と対策

| 事故 | 原因 | 対策 |
| --- | --- | --- |
| allowlist 登録の IP を解放してしまい外部連携が停止 | 未関連付け＝不要と誤認 | チェックリストで allowlist/DNS を確認 |
| 別リージョンで課金が残り続ける | 単一リージョンしか監査していない | 全リージョン監査 |
| disassociate しただけで課金が止まらない | release と混同 | release まで実施 |
| BYOIP を解放して持ち込みプールを喪失 | `PublicIpv4Pool` 未確認 | BYOIP を候補から除外 |
| 停止中インスタンス用の予約 IP を解放 | stopped インスタンスとの関連運用を未確認 | 事前ヒアリング |
