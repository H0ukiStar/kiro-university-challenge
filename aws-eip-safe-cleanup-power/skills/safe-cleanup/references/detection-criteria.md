# 「未使用 EIP」の判定基準

安全な削除は、正しい判定から始まる。判定を誤ると稼働中のシステムから IP を剥がす事故になる。

## 基本の判定ロジック

`describe-addresses`（boto3 の `describe_addresses`）で割り当て済み EIP を全件取得し、次を未使用候補とする。

- **`AssociationId` を持たない（未設定または空文字）EIP**

`AssociationId` があるものは何らかのリソース（EC2 インスタンスまたは ENI）に関連付いているため、原則として使用中とみなし候補から除外する。

## 関連する識別子

| フィールド | 例 | 用途 |
| --- | --- | --- |
| `AllocationId` | `eipalloc-0123...` | **解放に使う ID**。VPC スコープの EIP はこれで release する |
| `AssociationId` | `eipassoc-0123...` | 関連付けの有無を示す。未使用判定の主キー |
| `PublicIp` | `52.x.x.x` | 人間が識別するためのアドレス |
| `NetworkInterfaceId` | `eni-0123...` | 関連付け先の ENI（あれば使用中） |
| `InstanceId` | `i-0123...` | 関連付け先の EC2 インスタンス（あれば使用中） |

## 誤検出の罠（重要）

「`AssociationId` がない＝安全に消せる」と機械的に判断してはいけない。次のケースを必ず疑う。

### 1. 停止中（stopped）インスタンス用に確保している EIP

`AssociationId` を持たない EIP でも、停止中インスタンスの再起動時に再アタッチする運用で意図的に確保していることがある。停止中インスタンスは自動割り当てのパブリック IP を失うため、固定 IP を維持したいユーザが EIP を「待機」させている。解放前に停止中インスタンスとの関連運用がないか確認する。

### 2. セカンダリ ENI・未起動リソースへの割り当て予定

近い将来アタッチする前提でプロビジョニング済みの EIP がある。IaC（Terraform / CloudFormation）で管理されている EIP は、コンソール上「未関連付け」でも構成管理上は必要なリソースであることが多い。IaC の状態と突き合わせる。

### 3. allowlist / DNS / 外部連携に登録された固定 IP

現時点で未関連付けでも、ファイアウォールの許可リスト、パートナーの IP allowlist、DNS の A レコード、SaaS 側の送信元 IP 登録などに使われている（予定の）アドレスがある。解放すると同じ IP は二度と取得できないため、これらの登録があると復旧不能になる。

### 4. BYOIP（持ち込み IP）

自社で持ち込んだアドレス空間に属する EIP は課金対象外であり、解放すると持ち込んだプールから外れる。`describe-addresses` の `PublicIpv4Pool` が `amazon` 以外（自社プール ID）なら BYOIP。解放候補から除外する。

### 5. リージョンの見落とし（逆方向の罠）

これは「消しすぎ」ではなく「見落とし」の罠。EIP はリージョン単位。普段使わないリージョンに課金対象が眠っていることが多い。監査は全リージョンで行う。

## 判定フロー（推奨）

```
describe-addresses で全件取得
  └─ AssociationId あり? ── はい ─▶ 使用中（除外）
        │
        いいえ
        ▼
  PublicIpv4Pool が amazon 以外（BYOIP）? ── はい ─▶ 除外
        │
        いいえ
        ▼
  停止中インスタンス / IaC / allowlist / DNS で必要? ── はい ─▶ 除外（要ヒアリング）
        │
        いいえ
        ▼
  未使用候補として一覧化 ── ドライラン提示へ
```

最後の「必要か?」の判定は API だけでは確定できない。ユーザ確認（対話確認・ドライラン）で人間の判断を挟むことが安全設計の中心になる。
